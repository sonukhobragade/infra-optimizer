# About these files

`configuration.csv` and `metrics.csv` in this directory were generated by
`scripts/fetch-azure-sample.mjs` from the **Azure Public Dataset (V2)**, a
production VM trace released by Microsoft.

- Dataset: https://github.com/Azure/AzurePublicDataset
- Licence: **CC-BY-4.0** (the rest of this repository is MIT)
- Paper: Eli Cortez, Anand Bonde, Alexandre Muzio, Mark Russinovich, Marcus
  Fontoura, Ricardo Bianchini. *Resource Central: Understanding and Predicting
  Workloads for Improved Resource Management in Large Cloud Platforms.* SOSP
  2017.

If you publish anything derived from these files, the CC-BY-4.0 attribution
requirement applies to you as well.

## What is real and what is not

**Real, from the trace:** the CPU columns. `Cpu %` is each VM's average CPU
utilisation and `Max Cpu %` is its maximum, both as recorded by Azure. The core
count and memory size in `configuration.csv` are the VM's actual allocation.

**Not real:**

- **`Avg Memory %` and `Max Memory %`.** The trace records how much memory each
  VM was allocated but never how much it used. These columns are generated from
  the VM's own CPU figures by `syntheticMemoryPercent`, deterministically so the
  files are reproducible. They are a plausible shape, not a measurement.
- **`Min`, `Max`, `Current`, `Desired`.** A VM trace has no replicas and no HPA.
  These are derived from the group's mean CPU so the fleet is uneven rather than
  uniform.
- **The service names.** There are no services in a VM trace. VMs are grouped by
  workload category and machine shape, and each group is presented as a service
  with its member VMs as usage samples. The grouping is this repository's
  construct; the numbers inside each group are Azure's.

So: a CPU recommendation computed from these files rests on real production
usage. A memory recommendation does not. Do not cite one as evidence.

## Regenerating

```bash
node scripts/fetch-azure-sample.mjs --out sample-data/azure --services 10 --samples 8
```

The source file is about 440 MB compressed. The script streams it and aborts
the request once it has enough rows, so the actual transfer is a few megabytes
and the run takes under a second.
